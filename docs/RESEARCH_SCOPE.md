# Цель и границы анализа TM2309

**Текущая работа, проценты и чек-листы: [GitHub Issue #2](https://github.com/KobaProduction/redmibook-firmware/issues/2).** Здесь находятся постоянные правила и цель, а не изменяемый журнал задач.

## Для чего проект

На основе заводского BIOS ноутбука **Xiaomi RedmiBook Pro 16 2024 (TM2309)** восстановить все потенциально полезные владельцу **аппаратные интерфейсы обмена данными и управления**, чтобы позднее создать переносимые адаптеры для **Windows и Linux**. Не проектировать возможности только под WMI/Windows: рассматривать штатные средства ОС, драйверы, ACPI, UEFI Runtime Services, системную телеметрию, EC, Intel IPF/DPTF, PCI/USB-C/Thunderbolt и другие подтверждённые пути.

Продуктовая ценность: энергопотребление и лимиты процессора; батарея и её ресурс; адаптер и USB-питание; мониторинг температур, RPM, зарядки и нагрузки; заводские режимы охлаждения и производительности; при подтверждённой доступности — управление вентиляторами, микрофоном, подсветкой, устройствами, частотами и напряжениями.

Полная замена заводской BIOS **не является текущей задачей**. Если позднее пользователь отдельно запустит проект собственной прошивки, определим для него новые границы, сборку, восстановление после сбоя и критерии приёмки. Не переносить старую стратегию «собрать open BIOS» в текущие задачи автоматически.

## Обязательный критерий подключения исполняемого модуля

Для **каждого нового PE32/TE/иного нативного модуля**, нужного активной цепочке, сразу создать или подтвердить **полный высокоуровневый базис в каноническом Analysis**: корректная загрузка/архитектура → полный Ghidra-автоанализ через job → Ghidra C для **всех распознанных нативных функций** → проверка входящих/исходящих межмодульных зависимостей и их привязка к реальным поставщикам. Доказанные связи сохранять; неоднозначные фиксировать с уровнем **Вероятно** и явной неизвестной частью, не создавать вымышленные машинные `CALL/XREF`.

**Приёмка модуля:** проверенные счётчики `native functions / C success / C failed / unsupported / external stubs`, входящие и исходящие зависимости активного контура, сохранение программы и контрольное чтение C-индекса и ссылок. Ошибки C, существенные неизвестные связи и противоречия остаются открытыми блокировками, а не статусом «полностью обработан». Доказанно завершённый модуль не переанализировать повторно; независимые модули прошивки не линковать ради количества. Для ACPI AML использовать ASL, для данных — их естественное представление.

Исполнительный порядок — в [процессе анализа](ANALYSIS_PROCESS.md); это постоянное правило, не зависящее от текущей строки Issue #2.

## Сейчас: анализ и восстановление поведения

- Основной образ: установленная линия **A0A, 2024-06-04**; другие релизы только для адресной проверки различий.
- Сначала широкий обзор потенциально полезного оборудования и интерфейсов ОС, включая малоисследованные USB-C/Thunderbolt, параметры дисплейной матрицы, CPU/GPU/RAM voltage/clock и необычные EC-сервисы.
- Для доступного из ОС либо обоснованно перспективного пути — восстановить источник → вызов/данные → обработчик → реальный сенсор/аппаратную операцию → ограничения/обратную связь. Сохранять семантические названия, типы и доказательства в Analysis.
- Если вендорский обработчик только сохраняет Setup, возвращает успех без применения или выдаёт EFI_UNSUPPORTED — честно отделять **хранимое значение**, **поведение кода** и **исполнение на устройстве**. Не углубляться в заведомо пустой маршрут без нового свидетельства.
- Можно кратко заходить в любую часть BIOS, если это помогает установить аппаратного владельца или путь из ОС; не восстанавливать UI, стандартный код UEFI, библиотеки и загрузчик ради самих себя.

## Как оценивать 0–100%

**0%** — направление не изучено; **25%** — установлены признаки/примерные владельцы; **50%** — выделены интерфейсы, форматы, базовая логика; **75%** — восстановлены существенные аппаратные переходы и ограничения; **100%** — всё доступное по исходному BIOS поведение конкретного направления восстановлено статически, противоречия разрешены или явно ограничены, неизвестные места не скрыты.

**Не входят в шкалу:** запуск нашего кода, разработка приложения, сборка собственной прошивки, физическая проверка на ноутбуке, flash/recovery, стабильность на Windows/Linux. Успех одной функции не даёт 100% целой подсистеме. Старые проценты с иной границей не переносить молча. В Issue хранить числитель/знаменатель там, где они известны, иначе явно помеченную экспертную оценку.

Обычная работа — **без коммитов**. Изменения Analysis сохранять там же; после значимого продвижения обновлять Issue. Разработка или изменение Git-файлов — только по отдельному прямому запросу пользователя.
