# Процесс аппаратного анализа

## Вход и контекст

Основной вход: [AGENTS.md](../AGENTS.md) → [цель](RESEARCH_SCOPE.md) → [Issue #2](https://github.com/KobaProduction/redmibook-firmware/issues/2) → карта нужного домена → канонический Analysis.

При «освежи контекст» открыть заново указанную обязательную цепочку, [словарь](TERMS.md), а также актуальные [hardware-reverse](https://github.com/ArthurKoba/ai-agent-workflow/tree/main/skills/hardware-reverse) / [reporting](https://github.com/ArthurKoba/ai-agent-workflow/blob/main/docs/REPORTING_PROTOCOL.md) правила. Детальные инструкции о сессиях и восстановлении Analysis — `skills/hardware-reverse/analysis-project-lifecycle.md`; не читать все документы каждого раздела просто на всякий случай.

## Рабочий цикл

1. Из Issue выбрать малоисследованную **полезную для ОС** функцию/блок либо новое неизвестное аппаратное ребро.
2. В каноническом Analysis найти один реальный источник: API ОС, ACPI/UEFI-переменную, EC/PCI/MMIO-участок, сервисную таблицу либо BIOS-обработчик.
3. Ограниченно пройти ссылки, вызовы и поток данных **до следующего существенного решения**. Машинные инструкции — для спорных фактов; не тратить проход на негативный census или повторение уже закрытого пути.
4. В Analysis назвать владельца, функцию, структуры, указатели, конкретные регистры и связи; технические идентификаторы оставить точными. Поставить **Подтверждено / Вероятно / Неизвестно / Противоречие**, задокументировать источник и пробел. Не переименовывать одну и ту же физическую сущность разными именами и не объединять объекты только из-за одинаковой цифры.
5. Сохранить Analysis. Изменить таблицу/галочку Issue **только при содержательном приросте или пересмотре гипотезы**, показать `было → стало` для направления. Не приравнивать синтаксические переименования к восстановлению поведения.

**Чёткая граница:** обнаруженная запись в Setup, ACPI-описание, OEM-заглушка или возврат EFI_SUCCESS ещё не доказывают возможность управления из Windows/Linux. Разделять статически подтверждённый BIOS-путь, осуществимый OS-путь и физический readback. Не выполнять записи в EC/CMOS/MSR/SMM/UEFI и не прошивать ноутбук на текущем этапе.

## Терминология и отчёты

Использовать «анализ», «восстановление поведения», «аппаратный контракт», «маршрут данных/управления», а не разные слова для одного статуса. В ответах пользователю — понятные русские назначения вместо аббревиатур. Специфические аппаратные названия расшифровывать через [словарь](TERMS.md).

В обычном ответе: **только изменившиеся оценки** `было → стало`, одна-две новые значимые находки, препятствия/следующий шаг. Полная карта — по запросу; её актуальное состояние в Issue. 100% относится только к восстановлению логики по исходному образу, не к реальной плате.

При противоречии не маскировать его в «почти готово» — снизить уверенность, нейтрализовать ошибочный нейминг и зафиксировать в Analysis/Issue. Если важный старый Git-документ содержит ещё не перенесённые сведения, удерживать его до доказанной миграции, но **не использовать как вторую техническую истину**.
